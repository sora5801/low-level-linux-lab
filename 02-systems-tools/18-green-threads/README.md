# Green threads / coroutines 🟥

**What it is.** A working cooperative green-thread (coroutine) library for
x86-64 Linux, built up from the metal: first the *idea* via libc's
`makecontext`/`swapcontext`, then a **hand-written context switch in assembly**
(`switch.S`) that saves the callee-saved registers, swaps stacks, and resumes a
different task. Each task gets its own `mmap`'d stack with a `PROT_NONE` **guard
page** below it to turn stack overflow into an immediate SIGSEGV. On top of the
raw switch sits a small **round-robin scheduler** with `spawn`, `yield`, and
`join`.

**Difficulty: 🟥 (giant).** This ships a genuinely working **teaching core**,
not a production runtime. It is honest about the boundary — see
[Scope](#scope-what-this-does-and-does-not-do) below. The star artifact is
`switch.S`: ~20 instructions that are the entire reason green threads are cheap.

## What you'll learn

- The **System V AMD64 ABI** from the inside: which registers are callee-saved
  (`rbx, rbp, r12-r15`, plus `rsp`) and **why saving exactly those six + rsp +
  the return address is sufficient** to make a switch invisible to the caller.
- How a "context" can be *just a saved stack pointer* — every other register
  lives on the task's own stack.
- **`swapcontext`/`makecontext`** (`<ucontext.h>`): the libc primitive, its
  `uc_link`/`uc_stack` fields, and why a cooperative scheduler can do better.
- **`mmap(2)` + `mprotect(2)`** to build a stack with a guard page; how stacks
  grow downward and why the guard therefore goes at the *low* end.
- The **fake initial stack frame** trick: synthesising the bytes a fresh task
  needs so the very first switch "returns" into a trampoline with the entry
  function and argument already in registers.
- A **run queue + scheduler loop**: spawn / yield / join as cooperative state
  transitions with zero kernel involvement per switch.

## How it works (file by file)

- **`switch.S`** — the hand-written switch. `gt_switch(from, to)` pushes the six
  callee-saved registers onto the current stack, stores `rsp` into `from`, loads
  `rsp` from `to`, pops the six registers back off the *new* stack, and `ret`s.
  The return address is already on the stack (from the `call gt_switch`), so the
  same `ret` resumes a mid-yield task *or* launches a brand-new one. Also here:
  `gt_trampoline`, the launch pad a new task first `ret`s into — it reads the
  entry function from `r12` and the argument from `r13` (planted in the fake
  frame), calls `fn(arg)`, then falls into `gt_coro_exit` when it returns.
- **`gt.c`** — the scheduler. `stack_alloc` mmaps a stack and `mprotect`s the
  low page to `PROT_NONE`; `frame_init` writes the seven-word fake frame;
  `runq_push`/`runq_pop` are the intrusive FIFO; `gt_spawn`/`gt_yield`/`gt_join`
  are the primitives; `gt_run` is the scheduler loop that switches into each
  ready task and reclaims dead ones with `munmap`.
- **`gt.h`** — the public API and the `gt_context` (a single `rsp`) the assembly
  depends on. The comment on `gt_context` states the offset-0 invariant.
- **`main.c`** — the driver: three workers round-robin via `yield`, then a
  supervisor `spawn`s and `join`s two children.
- **`ucontext_demo.c`** — the same ping-pong idea using libc's ucontext API, for
  comparison. It explains why we ultimately hand-roll the switch (no per-switch
  `sigprocmask`, no deprecated API, and you get to *see* the ABI).
- **`guard_demo.c`** — a task that recurses without bound; watch the guard page
  convert the overflow into a clean SIGSEGV instead of silent corruption.

### The context switch, in registers

`gt_switch` preserves exactly the callee-saved set because, to the C compiler,
it is an ordinary function call: the compiler has **already** spilled any live
*caller-saved* registers (`rax, rcx, rdx, rsi, rdi, r8-r11`) around the call, so
we get that saving for free. What a correct function must return unchanged is
the callee-saved set — so that is all we save:

```
push rbp; push rbx; push r12; push r13; push r14; push r15   # save 6 regs
mov  %rsp, (%rdi)        # from->rsp = rsp        (park outgoing task)
mov  (%rsi), %rsp        # rsp = to->rsp          (STACK SWAP)
pop  r15; pop r14; pop r13; pop r12; pop rbx; pop rbp         # restore 6 regs
ret                      # pop return address off the new stack, jump to it
```

### The fake initial frame (how a new task starts)

A new task has never been switched away from, so nothing has pushed the state
`gt_switch` expects to pop. `frame_init` fabricates it — seven words below the
16-aligned stack top:

```
rsp -> [ r15=0 ][ r14=0 ][ r13=arg ][ r12=fn ][ rbx=0 ][ rbp=0 ][ ret=gt_trampoline ]
```

The first `gt_switch` into the task pops those six registers (so `fn` lands in
`r12`, `arg` in `r13`) and `ret`s into `gt_trampoline`, which calls `fn(arg)`.
Because the frame is exactly 56 bytes and the top is 16-aligned, `rsp` is
16-aligned again on entry to the trampoline — so `fn` sees an ABI-legal stack.

## Assembly notes

Two assembly artifacts ship here:

1. **`switch.S`** — the *real* project code, hand-written and heavily annotated.
   This is the file to study: it is the actual context switch the demos link
   against (`make asm` re-assembles it to prove it is valid). Its header block
   walks the ABI and explains, register by register, why the callee-saved set is
   both necessary and sufficient.
2. **`asm/demo.annotated.s`** — clang's `-O1` output for `asm/demo.c` (the
   scheduler's pure pick-next / run-queue logic), annotated instruction by
   instruction. `demo.c` is a self-contained slice of `gt.c` — same struct
   offsets, no syscalls — so it cross-compiles cleanly. Highlights the annotation
   draws out: `align_up` computing the mask `~(a-1)` as `-a`; the singly-linked
   unlink in `pick_next` (keep `prev`, bridge over the removed node, fix the
   tail); and `frame_init` folding four zero-slots into two 16-byte SSE stores —
   the same seven words `switch.S` pops, so read them side by side.

Compare the optimization levels:

- [`asm/demo.O0.s`](asm/demo.O0.s) — naive, every value spilled to the stack.
- [`asm/demo.s`](asm/demo.s) — `-O1`, the annotated baseline.
- [`asm/demo.O2.s`](asm/demo.O2.s) — `-O2`, `demo_main` inlined and folded.

## Scope (what this does and does not do)

**Does** (the working teaching core):
- Cooperative **N:1** scheduling: many tasks on one OS thread, switched in user
  space with the hand-written `switch.S`.
- `spawn`, `yield`, `join`; a FIFO round-robin run queue.
- Per-task `mmap` stacks with `PROT_NONE` guard pages; `munmap` on task death.

**Does not** (honest gaps, addressed in *Going further*):
- **No preemption.** A task that never yields runs forever. Real runtimes use a
  timer signal (see below).
- **Not truly M:N.** Everything runs on one OS thread. A real M:N runtime runs
  several worker OS threads, each with a run queue, plus **work-stealing** and
  the synchronisation that demands. This core keeps the globals lock-free by
  keeping the parallelism at one — the honest simplification for a first pass.
- **Single joiner per task**, no task-local storage, no cancellation, and dead
  task structs are freed at `gt_run` teardown rather than reaped eagerly by an
  arbitrary number of joiners.

## Going further (the `Stretch:` from the list)

- **Preemption via a timer signal.** Arm `setitimer(ITIMER_PROF)` /
  `timer_create` to deliver `SIGPROF`/`SIGVTALRM` periodically; in the handler,
  set a "please yield" flag or directly `gt_switch` from the signal frame back
  to the scheduler. The hard parts are (a) making the switch async-signal-safe
  and (b) protecting the run queue from the handler — which forces the same
  memory-ordering discipline `19-sync-primitives` explores.
- **True M:N with work-stealing.** Give each worker OS thread its own run queue;
  idle workers steal from the back of a victim's deque (Chase–Lev). Now the
  queue operations need atomics/`acquire`/`release`, and stacks migrate between
  threads — this is essentially the Go runtime's scheduler.
- **Async I/O.** Drive the scheduler with `epoll` or `io_uring`: a task that
  would block on a socket instead registers interest and yields; the scheduler
  parks it until the readiness event, then re-queues it. This is how green
  threads become useful for servers (the Go netpoller, Rust's Tokio).
